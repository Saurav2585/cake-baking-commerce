## 0. Independent findings not raised by Wave 1 (read this section first)

These are gaps this review found by checking the actual test/tooling infrastructure the five documents assume exists, rather than by re-reading their claims. None of the five documents is wrong about anything below — they simply didn't have this specific infrastructure question in scope. It matters for this acceptance plan because several of the required verification methods (§5, §6, §7) depend on tooling that does not currently exist in this repository.

1. **There is no real cross-browser test matrix today — `playwright.config.ts` only exercises Chromium.** Both configured projects (`desktop`, `mobile`) use `devices["Desktop Chrome"]` as their base; the "mobile" project is Chromium with a narrow viewport and `isMobile`/`hasTouch` flags, not a real mobile browser engine, and there is no WebKit or Firefox project defined anywhere in the config. None of the five Wave 1 documents claim otherwise, but none of them flag it either, and §5/§6's numeric budgets and interruption tests below are only automatable against Chromium as the repo stands — real Safari/WebKit and Firefox verification will be manual unless a `webkit`/`firefox` Playwright project is added. This is called out explicitly in §6.
2. **`tests/accessibility/` is an empty placeholder — no automated accessibility testing exists in this repo today, and no accessibility testing library is installed.** The directory contains only a `.phase-placeholder` file. `package.json`'s `devDependencies` has no `axe-core`, `@axe-core/playwright`, `jest-axe`, or any equivalent. Every accessibility acceptance criterion in §7 below must therefore specify whether it assumes a new devDependency is added (this plan recommends `@axe-core/playwright`, since Playwright is already the e2e tool) — this is a real, previously-unflagged gap, not an oversight in phrasing: none of the five Wave 1 documents mention that automated a11y tooling doesn't exist yet, because none of them had reason to look at `tests/accessibility/`'s actual contents.
3. **The existing e2e suite is a single flat file, `fullyParallel: false`, `retries: 0`, no CI config found in-repo.** Four tests, ~65 lines total, run serially. Any new coverage this plan asks for (§1, §5, §7, §9, §10) will materially grow this file or require new spec files under `tests/e2e/`; Frontend_GSAP_Architecture.md's Worktree 4 already anticipates new spec files, so this is consistent, but the serial/no-retry config means a genuinely flaky new motion-interruption test (§5.4) will surface as a hard failure, not a retried pass — acceptance sign-off should not quietly loosen `retries` to paper over a real flake without root-causing it first.
4. **Contradiction to flag for orchestrator reconciliation (stated in the task brief, independently reconfirmed here): the `.plp-card`/`.product-card` naming tension is real and unresolved in writing.** `Route_UI_Specification.md` §1.1 explicitly designs new `.plp-card`/`.plp-grid` classes, distinct from `.product-card`/`.product-grid`, specifically because `CatalogProduct` has no `badges[]` field the way `.rp-card`'s homepage-only curatorial data does. `Frontend_GSAP_Architecture.md` §2 explicitly requires the converged grid-variant card to **keep** the root class `.product-card` (never rename it, never alias it) specifically so `tests/e2e/critical-journeys.spec.ts`'s `.product-card` selector never breaks. Both documents were produced in the same gate, reference each other's existence, and neither one's Handoff section flags this naming collision to the other. This review's verification plan (§3, §6) is written to be resolution-agnostic per the task brief's own framing — but flags explicitly in the Handoff below that this is a decision the orchestrator must make in writing before implementation starts, not something an implementer should resolve silently by picking whichever reads better in the diff.
5. **A second, smaller naming/scope question the five documents leave open:** Route_UI_Specification.md's new image-canvas classes are named `.plp-image`, `.category-image`, `.search-image`, `.pdp-hero-image` (four different class names for one identical CSS rule, per its own §1.4 code block) while Frontend_GSAP_Architecture.md's migration plan never mentions these classes at all (it only discusses `.product-card`'s root class, not its internal image wrapper). If the PLP/Search/Category workstream and the card-convergence work land in the same PR, an implementer needs to decide whether the converged card's image wrapper is one shared class or four route-specific aliases of one rule — this plan's §3 verification (visual consistency check) is written to catch a *rendering* inconsistency regardless of which naming approach is chosen, but the naming ambiguity itself is worth flagging alongside item 4.
6. **The `Multi_Agent_Execution_Plan.md` file exists in the same directory (`production_artifacts/06_recovery_r2b2/Multi_Agent_Execution_Plan.md`) and was referenced by name in several Handoff sections but was not one of the six files this task was instructed to review.** It was not opened for this review, consistent with the task's explicit file list; noted only so the orchestrator knows it was deliberately out of scope here, not overlooked.

## 1. Functional commerce

**1.1 Cart/wishlist add-remove-persistence across the card convergence (`variant="rail"` vs `"grid"`)**
- **Method:** Extend `tests/e2e/critical-journeys.spec.ts` (or a new sibling spec) with a test that: (a) on `/` (homepage rail, `variant="rail"`), clicks a rail card's Quick-add button, asserts cart count increments by 1 via the header badge text and via `localStorage.getItem("pantryform:cart:v1")` parsed JSON; (b) on `/shop/ingredients` (PLP grid, `variant="grid"`), repeats the same add for a *different* product; (c) navigates to `/cart` and asserts both lines are present with correct `sku`/`quantity`/`productTitle`; (d) removes one line via `removeLine`, asserts the other survives untouched; (e) reloads the page (full navigation, not SPA transition) and asserts the surviving line persists — this is the actual regression surface the convergence work touches, since both variants must now emit byte-identical `addLine()` payload shapes per Frontend_GSAP_Architecture.md §2 step 1.
- Repeat the same sequence for `toggleWishlist()` from both variants, asserting `/wishlist` shows both products and that removing one via the PLP grid variant does not affect one added via the rail variant.
- **Acceptance bar:** cart/wishlist state added from a `variant="rail"` card and a `variant="grid"` card must be indistinguishable in the persisted `CartState`/wishlist array shape — no `variant`-conditional field, no rail-only or grid-only cart line property.

**1.2 Homepage PDP-link regression (Frontend_GSAP_Architecture.md §0.3/§2 fix)**

## 3. Visual fidelity
