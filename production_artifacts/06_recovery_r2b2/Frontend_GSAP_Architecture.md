## 0. What is actually true about the codebase right now (read this before the rest)

Two premises in the task brief needed verification against the current tree; both were confirmed, and one important correction to a stale assumption follows:

1. **There is only one canonical catalog, not two.** `src/lib/domain/catalog.ts` reads `production_artifacts/05_catalog_production/Product_Master_Data.json` etc., and as of R2B1 (commit `15e621d`) that JSON already holds all **48 parent products / 51 SKUs / 30 brands** — this was previously the 24-product fictional catalog but has been fully migrated. `catalog` (the eager, synchronous, module-scope array) is consumed identically by `/shop`, `/shop/[department]`, `/shop/[department]/[category]`, `/search`, and `/products/[slug]` via `product-card.tsx` / `product-grid.tsx` / `shop-explorer.tsx` / `product-detail.tsx`. **These routes are already on the real catalog and already correct.** They are not blocked on this architecture doc; they are precedent for it.
2. **`src/data/real-products.ts` is not a second catalog.** Its own header comment says so, and the code confirms it: `realProducts` is derived via `.map()` over `catalog`, picking 12 of the 48 IDs and attaching homepage-only curatorial metadata (badge, note) that "has no canonical home" elsewhere. It is a *view*, not a *source*.
3. **Correction to the task brief's framing:** the brief describes `real-product-card.tsx` as used "only on the homepage" — confirmed true — and frames the convergence as combining "two card components." That is accurate, but there is a concrete, previously unflagged defect in the newer of the two: **`RealProductCard` (`src/components/real-product-card.tsx`) contains zero `<Link>` elements.** Neither the product image nor the title is wrapped in a link to `/products/[slug]`; only the wishlist heart and the "Quick add" button are interactive. Every homepage rail (bestsellers, new arrivals, essentials, tools/packaging — four rails, ~12-16 card renders) is currently a dead end for a shopper who wants product detail. `ProductCard` (the older component) does link the image and title to `/products/[slug]`. This is not a style preference; it is a functional gap that the convergence work must close, and it is called out explicitly in §2 below so it isn't lost as a "nice to have."
4. **`resolveMedia()` returns exactly one image per product (plus one thumbnail derivative), and per-variant media only where a variant has its own asset record.** There is no multi-image gallery data model anywhere in the manifest. `product-detail.tsx`'s "variant thumbnails" strip is the only existing multi-image UI, and it is multi-*variant*, not multi-*angle*. Any new motion/gallery treatment (image carousels, hover-swap, zoom pans) must be scoped to what `CatalogMedia` actually provides — one hero image, one thumbnail, optionally distinct images per variant — not invented per-product angle sets.
5. **`production_artifacts/06_engineering/Technical_Architecture.md` (pre-recovery) has diverged from reality in several structural ways.** It is treated here as informative precedent, not current truth, per the task instructions. Divergences, so nobody "fixes" the codebase to match a doc that no longer reflects an approved decision:
   - Doc specifies `src/domain/`, `src/providers/`, `src/motion/`, `src/data/`(-as-generated-projection). Reality: domain logic lives at `src/lib/domain/`; there is no `src/providers/` directory — `CommerceProvider` is a single React Context component co-located in `src/components/`; there is no `src/motion/` directory — all motion code is the single file `src/components/motion-enhancer.tsx`; `src/data/` holds a hand-written curatorial view (`real-products.ts`), not a generated catalog projection (the generated-feeling projection is `catalog.ts` itself, which imports the production-artifact JSON directly at module scope).
   - Doc's `CatalogProvider` / `ContentProvider` / `CartPersistence` / `CheckoutProvider` interface-boundary language does not exist as implemented abstractions — `catalog` is a plain synchronous export, and `CommerceProvider` talks to `localStorage` directly, not through a swappable persistence interface.
   - Doc says "Central motion utilities" (plural/utility-layer language) — reality is one component with one animation call.
   - None of this is a defect to fix under R2B2; it means new GSAP/PLP/PDP work should treat the *current directory layout* (`src/lib/domain`, `src/components`, `src/data`) as the real convention to extend, and should not resurrect the doc's `src/domain`/`src/providers`/`src/motion` paths wholesale without a scoped decision to do so. Where this document proposes a new `src/motion/` directory below (§4), it is a deliberate, narrow adoption of that one piece of the old doc's grouping — not a wholesale reconciliation.

## 2. Shared product-card migration path

**Current state:** two components. `product-card.tsx` (root class `.product-card`, links image+title to `/products/[slug]`, has a numbered `.card-index` badge, plain "Save"/"Saved" wishlist button, no add-to-cart button, consumes `CatalogProduct`) is used by `ProductGrid`, which is used by `/shop`, `/shop/[department]`, `/shop/[department]/[category]`, `/search`, and PDP's related-products rail. `real-product-card.tsx` (root class `.rp-card`, no PDP link at all — see §0.3, brand eyebrow + badge pill + heart-icon wishlist toggle + "Quick add" button, consumes the homepage-only `RealProduct` type) is used only by `real-product-rail.tsx`, used only by `src/app/page.tsx`.

**Target state:** one canonical card component, `product-card.tsx`, consuming `CatalogProduct` everywhere, with an optional presentation variant so the homepage's denser/more visual rail treatment and the PLP's denser grid treatment can both be served without forking the component again.

**Constraint that shapes the whole plan:** `tests/e2e/critical-journeys.spec.ts` does `page.locator(".product-card").first()` on `/shop/ingredients` and `.toHaveCount(4)` on `/search?q=cocoa`. Both assertions are scoped to non-homepage routes today, so a homepage-only migration step cannot break them — but the **moment the homepage starts rendering the converged card, the root class must still be `.product-card`** (not `.rp-card` retained as an alias, and not a new class), or a future test that broadens its selector to include the homepage will silently pass against the wrong markup. The migration order below is built to never produce an intermediate state where `.product-card` exists on a page but with different semantics/behavior than the e2e test expects, and never removes `.product-card` from a page the test already asserts against.

**Migration order:**

1. **Extend `product-card.tsx` in place, additively.** Add an optional `variant?: "grid" | "rail"` prop (default `"grid"`, preserving exact current behavior/markup for all five existing consumers with zero visual change) and optional `badge?: string`. Under the hood, add the presentation pieces `RealProductCard` has that `ProductCard` currently lacks — a heart-icon wishlist toggle as an alternative render path to the current "Save"/"Saved" text button, and an optional "Quick add" button — gated behind `variant === "rail"`. Critically: **the PDP link (image + title → `/products/[slug]`) is added unconditionally to the rail variant**, closing the §0.3 gap as part of this step, not as an afterthought. The root element keeps `className="product-card"` in both variants (rail can add a second modifier class, e.g. `"product-card product-card--rail"`, but must never drop the base class). No consumer is touched in this step; this step is pure library-side capability addition and is safe to land and test in isolation (component/unit tests, no route changes).
2. **Point the homepage at the converged card.** Change `real-product-rail.tsx` (or fold it away entirely and call `ProductGrid`/`ProductCard` directly from `src/app/page.tsx`) to render `<ProductCard product={p} variant="rail" badge={...} />` where `p` is a `CatalogProduct` pulled straight from `catalog`, not a `RealProduct`. The badge assignment table currently in `src/data/real-products.ts` (`HOMEPAGE_SELECTION`) is preserved as-is and re-exported as a lookup keyed by canonical product ID — it is presentation-only curatorial metadata with legitimately "no canonical home" (per its own doc comment), so it is not folded into `catalog.ts`; it just now feeds a `badge` prop into `ProductCard` instead of populating a parallel `RealProduct` object. This step changes homepage markup only. `.product-card` now appears on the homepage for the first time; because the e2e mobile-drawer/reflow test (`mobile navigation and 360px reflow`) and the reduced-motion test both hit `/` and neither currently asserts on `.product-card` count or content, this is safe. Verify manually (or with a new, narrowly-scoped test — see §6) that homepage `Quick add` / wishlist-heart / PDP-link behavior is unchanged from the pre-migration `RealProductCard` behavior, plus the new working PDP link.
3. **Delete the deprecated files.** Once step 2 is verified, delete `src/components/real-product-card.tsx` and `src/components/real-product-rail.tsx`, and trim `src/data/real-products.ts` down to just the badge/curation map (drop the `RealProduct` interface, `toRealProduct()`, `realProductsById`/`realProductsByBadge` helpers that exist only to shape the now-unused parallel type — replace with equivalent helpers that filter `catalog` directly by the badge map's keys). Update `src/app/page.tsx`'s imports accordingly. This step is a pure deletion/rename with no behavior change if steps 1–2 were done correctly, so it is low-risk and can be a fast-follow in the same PR or a same-day follow-up.
4. **Do not attempt to also merge in a third "spreadsheet grid" numbering scheme or a fourth visual treatment in this pass.** `product-card.tsx`'s `.card-index` numbered badge is grid-variant-only and stays grid-only; it was never part of the homepage's visual language (confirmed against `design_review/recovery_r2a_rework/screenshots/03-desktop-product-cards-closeup.png`, which shows badge pills, not numbers) and should not appear on rail-variant cards.

This order guarantees: (a) the e2e `.product-card` selector never observes a broken intermediate state, because steps 1 and 2 are additive/behavior-preserving until the moment they're verified, and step 3 only removes already-dead code; (b) the PDP-link gap gets fixed as a byproduct of convergence rather than needing a separate pass over `RealProductCard`; (c) `product-card.tsx` remains under sole write ownership of one workstream throughout (§1), so PDP's related-products consumption of it never collides with PLP's migration edits.

## 3. Canonical catalog data consumption pattern for new client components

`catalog` is a plain synchronous array computed once at module load (`src/lib/domain/catalog.ts`), not an async fetch — there is no real "loading" boundary to design around, and no workstream should introduce one (no `useEffect` + `fetch('/api/products')`, no client-side re-derivation of what a server component already computed). The existing, correct pattern — and the one every new PLP/PDP/motion client component must follow — is:

- **Server components import `catalog` (or a filtered/sliced view of it) directly at module scope and pass the resulting plain data down as props to client components.** This is what every existing route already does (`/shop`, `/shop/[department]`, `/search`, `/products/[slug]` all import `catalog`/`catalogBySlug` server-side and hand a `CatalogProduct[]`/`CatalogProduct` down). Client components (`shop-explorer.tsx`, `product-card.tsx`, `product-detail.tsx`) receive catalog data as props and never import `catalog` themselves for data they could receive as props — the one narrow exception today is `real-products.ts`, which is itself imported at module scope by the (server) `src/app/page.tsx`, i.e. still server-side, not inside a client component.
- **A client component may import `catalog`/`formatINR`/etc. directly only when it has no server-component parent that could pass the data as a prop** (there is no such case in the current tree — every catalog-consuming client component already has a server parent). Do not introduce one for convenience; it defeats server-side computation and risks the module-scope `resolveMedia()` throw (§0, `catalog.ts` L120–138) happening inside a code path that's harder to trace.
- **48 products / 51 SKUs does not warrant pagination or virtualization**, and no PLP work in R2B2 should add either. `ShopExplorer` already renders the full filtered set client-side with no windowing and no reported performance concern; a "full PLP grid" at 48 items is not a scale problem for `next/image` + CSS grid. Revisit only if a future catalog expansion moves the count into the hundreds — not a decision this document makes, just a threshold to flag if it comes up.
- **Media resolution stays server-side.** `resolveMedia()` and `resolveRecipeMedia()` are synchronous, throw-on-missing-asset functions; they should continue to be called from server components/module scope (as `catalog.ts` and `product-detail.tsx` already do — note `product-detail.tsx` is `"use client"` but calls `resolveMedia()` inside a `useMemo` keyed on already-validated `product.id`/`variant.id` that came from server-supplied props, so the throw surface is bounded to variant IDs that are known-valid at render time, not user input). Do not call `resolveMedia()` with any client-derived or unvalidated ID.

## 4. GSAP module boundaries and ScrollTrigger contract

**Where scopes live.** `gsap.context()` scoping stays exactly where the task brief describes it: one scope per mounted `<MotionEnhancer>` tree, created in a `useLayoutEffect`, reverted on unmount via `context.revert()`. New motion work extends this pattern rather than inventing a second scoping mechanism:

- **`MotionEnhancer` stays the outer scope for whole-page/section reveal animation** (the existing `[data-measure-reveal]` pattern). It is not moved or renamed.
- **New scroll-driven work (parallax collage, pinned sections, scroll-synced reveals) gets its own hook(s) in a new `src/motion/` directory**, each creating its *own* `gsap.context()` scoped to a `ref` on the specific DOM subtree it animates, with its own `useLayoutEffect` cleanup. Do not add ScrollTrigger instances inside `motion-enhancer.tsx`'s existing context — that context's only job is the mount-time reveal, and mixing a one-shot reveal context with a resize/scroll-reactive ScrollTrigger context makes `context.revert()` cleanup timing harder to reason about (revert must run for both on unmount/route change, but the reveal context has no reason to ever need `ScrollTrigger.refresh()` behavior, and giving it that dependency for no reason increases the blast radius of any ScrollTrigger bug).
- Proposed `src/motion/` contents (new files, Motion workstream owns; none of these exist yet):
  - `src/motion/gsap-client.ts` — a client-only module whose entire job is `gsap.registerPlugin(ScrollTrigger)`, guarded so it only ever executes in the browser (see SSR guard below), and idempotent (registering twice is harmless in GSAP but the guard should still make intent explicit rather than relying on that).
  - `src/motion/tokens.ts` — shared duration/ease/stagger constants and `gsap.matchMedia()` breakpoint strings, so the existing `0.72`/`power3.out`/`0.07` values in `motion-enhancer.tsx` and any new hook's values come from one place instead of being re-typed as magic numbers per file.
  - `src/motion/use-scroll-reveal.ts` (or similarly named hooks, one per motion pattern actually specified by the visual/choreography agents — this document does not invent the choreography, only the plumbing) — each hook takes a `ref`, creates its own `gsap.context()`, registers `ScrollTrigger`s inside it, and returns cleanup via the standard `useLayoutEffect` return.

**`gsap.matchMedia()` for responsive variants.** Any animation whose parameters differ by viewport (e.g., hero collage parallax disabled or reduced below a breakpoint, rail stagger count differing mobile vs. desktop) must express that via `gsap.matchMedia()` inside the relevant `gsap.context()`, added with `context.matchMedia()` (the context-scoped form, so its conditions are torn down by the same `context.revert()` as everything else in that scope) rather than a bare module-level `gsap.matchMedia()` call that would outlive the component. Breakpoints should reuse `src/motion/tokens.ts` constants rather than each hook hardcoding its own `"(min-width: 768px)"` strings.

**ScrollTrigger registration — client-only, SSR-guarded.** `gsap.registerPlugin(ScrollTrigger)` touches `window`/`document` at module evaluation in some GSAP versions' plugin init paths and must never execute during server rendering or during the module-graph evaluation that happens for a Server Component import. Concretely:
- `src/motion/gsap-client.ts` must be imported only from files that are themselves `"use client"` (never from `src/app/**/page.tsx` server components, never from `src/lib/domain/**`).
- Registration must happen inside a `useLayoutEffect` (not at module top level), mirroring the existing `motion-enhancer.tsx` pattern of doing all GSAP work inside the effect, not at import time. Do not rely on "it's fine because Next only runs client components in the browser after hydration" as the sole guard — the same client-component module can still be *evaluated* in a server-rendering pass for tree-shaking/RSC boundary analysis in some bundler configurations, so the actual `gsap.registerPlugin()` call itself, not just its import, must be effect-gated.

**The start/end/scrub/pin contract every ScrollTrigger implementer must follow:**
- **`start`/`end` are always expressed in relative/percentage terms tied to the triggering element** (e.g. `"top 80%"`, `"bottom top"`), never bare pixel offsets — bare pixel triggers break the moment fonts/images shift layout after first paint (see next point) and break again on any content-length change from future catalog edits.
- **`scrub` defaults to a numeric value (e.g. `scrub: 0.5`–`1`), not `true`/bare boolean**, for anything with perceptible duration, so the animation has inertia/smoothing instead of being rigidly bound to scroll position on every frame — bare `scrub: true` is acceptable only for very short, purely decorative micro-parallax where 1:1 scroll coupling is the explicit intent.
- **`pin` is opt-in per instance, never a default,** and any pinned section must set an explicit `pinSpacing` decision (don't leave it to the ScrollTrigger default without a conscious check against the surrounding `section-shell`/`page-shell` layout rhythm used throughout `globals.css`) and must be verified against the mobile-drawer/reflow e2e test's 360px-width assertion (`overflow` must remain `0`) — pinning is a common source of introduced horizontal overflow on narrow viewports if the pinned element's width isn't constrained independently of its unpinned layout width.
- **`invalidateOnRefresh: true` is required on any ScrollTrigger whose animated properties depend on measured start values that can change with viewport/content reflow** (essentially: any trigger using `y`, `x`, or pin distances derived from element size, which is nearly all of them in this codebase's editorial/collage-heavy layout). Without it, a browser resize (including the dev-tools/orientation-change-triggered resize the responsive test suite exercises) can leave stale start/end math in place.
- Every `ScrollTrigger.create()` or `scrollTrigger:` config used inside a `gsap.context()` is automatically reverted by `context.revert()` — implementers must not separately call `ScrollTrigger.kill()` on unmount as a redundant/competing cleanup path; one cleanup mechanism only, matching the existing `motion-enhancer.tsx` convention.

**Font/image load timing — the concrete first-paint bug and its mitigation.** This codebase is a heavy `next/image` + custom-font editorial layout (hero collage, department tiles, brand strip, four product rails all using `fill` images). ScrollTrigger computes trigger start/end positions from the DOM's *current* layout at the moment `ScrollTrigger.create()`/`.refresh()` runs. If that happens before images have reserved their final box (should not happen with `next/image`'s intrinsic `fill`+`sizes` sizing, which reserves layout space immediately — but *does* happen if any custom font causes a FOUT/FOIT reflow after trigger creation, or if any future non-`next/image` decorative element lacks explicit dimensions), every trigger computed against a downstream element's position will be wrong on first scroll and only self-correct after a resize or manual refresh. Required mitigation for any implementer: (1) never compute triggers against elements whose box isn't yet determined by CSS/intrinsic sizing alone — `next/image` with `fill` inside an explicitly-dimensioned wrapper (the existing `.collage-frame`/`.tile-image`/`.rp-image` pattern already used throughout `globals.css`) satisfies this; (2) call `ScrollTrigger.refresh()` once after web fonts report ready via the standard `document.fonts.ready` promise, gated inside the same `useLayoutEffect`/`gsap.context()` as the trigger creation so the refresh is cleaned up identically; (3) prefer `invalidateOnRefresh: true` (above) as the general-purpose safety net rather than trying to perfectly sequence every load event by hand.

## 5. Transform/opacity-only preference, and when other properties are acceptable

Default to animating only `transform` (`x`/`y`/`scale`/`rotate`) and `opacity` — this is already the existing convention (`motion-enhancer.tsx` animates `y` and relies on `clearProps: "transform"` to hand the element back to normal layout flow after the reveal). These are the two property classes the browser compositor can animate without triggering layout/paint on every frame, which matters here specifically because ScrollTrigger-driven `scrub` animations re-evaluate on every scroll tick — a layout-triggering property under `scrub` is a frame-budget problem in a way a one-shot mount animation is more forgiving of.

Other properties are acceptable only narrowly:
- **`clearProps`** (already used) is not an animated property and is fine/expected — it's cleanup, not motion.
- **`filter` (blur/brightness) at small magnitudes** is acceptable for short, non-scrubbed reveal accents (e.g., a brief blur-in on the hero) — GPU-composited in modern browsers, but should not be used inside a `scrub`-bound ScrollTrigger where its cost repeats every tick.
- **`clip-path`** is acceptable for reveal/mask effects (e.g., a collage frame wiping in) under the same one-shot-preferred, avoid-in-scrub guidance.
- **Explicit `width`/`height`/`top`/`left` animation is not acceptable** anywhere in this codebase's motion work — every layout-affecting visual change achievable here has a transform-based equivalent (scale instead of width/height, translate instead of top/left), and the existing hero-collage/department-tile/rail layouts are all CSS Grid/Flexbox positioned, which composes cleanly with transform-based motion without needing box-model animation.
- If an implementer believes a specific effect genuinely requires a layout-triggering property, that is a documented exception to raise with the motion workstream lead before landing, not a silent choice — it should be rare enough in this catalog-card/editorial-section context that it's worth a second look every time it comes up.

## 6. Progressive enhancement, no-animation operation, dynamic `import()`, cart/variant independence, error handling — the safety contract

**Progressive enhancement / full no-animation operation.** The existing `motion-enhancer.tsx` already establishes the required posture and every new motion addition must preserve it exactly: (a) checks `prefers-reduced-motion` once at mount and does nothing if it matches — new hooks do the same check (via `gsap.matchMedia()`'s own reduced-motion-aware conditions, or an equivalent explicit check, consistently — not half the hooks using one mechanism and half using another); (b) if GSAP never runs at all (JS disabled, script failed to load, error thrown before the effect fires), the DOM is already in its final, fully usable, fully-styled state — animation only ever *moves* already-rendered, already-interactive content into place (the `y: 12 → 0` reveal), it never toggles `display`/`visibility`/mounts content that wouldn't otherwise exist. Any new pattern (pinning, scroll-scrub reveals) must follow the same rule: the pre-animation and post-JS-failure DOM state is the *same* final content, just without the transition. Concretely, never gate a section's presence in the DOM on a `ref` being populated or an animation having run — that turns "animation absent" into "content absent," which this codebase's existing pattern correctly avoids.
**Where dynamic `import()` is justified.** GSAP core is currently a top-level `import gsap from "gsap"` inside `motion-enhancer.tsx`, which is used by every route that wraps content in `<MotionEnhancer>` (today: the homepage; check before extending this to other routes). Because `gsap` is a `dependencies` (not conditionally loaded) package, and `motion-enhancer.tsx` is already imported broadly, GSAP core is likely already in the initial client bundle for any route using it — this document does not change that baseline. The clear, justified case for `import()` is **`ScrollTrigger` specifically**, and any future GSAP plugin (`Draggable`, `SplitText`, etc.) the choreography agents might call for: these are only needed by routes that actually use scroll-driven effects (plausibly the homepage hero/collage, plausibly not `/cart`, `/checkout`, `/wishlist`, information pages, or the recipe-review flow, none of which have any editorial/scroll-heavy layout today). Pattern: `src/motion/gsap-client.ts` dynamically imports `gsap/ScrollTrigger` inside the same `useLayoutEffect` that would register it (`const { default: ScrollTrigger } = await import("gsap/ScrollTrigger")`), so routes/components that never call into `src/motion/gsap-client.ts` never pull ScrollTrigger into their chunk at all. Do not dynamically import GSAP *core* itself unless a specific route is identified as GSAP-free and worth the async-mount flash-of-unanimated-content tradeoff that a dynamic core import introduces (none currently is — the existing `motion-enhancer.tsx` reveal is cheap enough and universal enough that static import is the right call for core).

**Cart/variant state independence from animation — explicit contract.** This is load-bearing and must hold in both directions:
1. **Animation code must never gate a commerce state transition.** No `addLine()`/`toggleWishlist()`/`setQuantity()`/`completeSimulation()` call (all defined in `commerce-provider.tsx`) may be wrapped in, awaited by, or made conditional on a GSAP tween, timeline, or `ScrollTrigger` callback completing. If a "quick add" button gets a satisfying press animation, the animation plays *alongside* (or after, fire-and-forget) the `onClick`'s `addLine()` call, never as a precondition for it. `commerce-provider.tsx`'s own state model already assumes this — `ready`, `cart`, `wishlist` are driven purely by `useReducer`/`useState` and `localStorage`/`queueMicrotask` timing that has nothing to do with animation; nothing in that file should ever need to know whether GSAP loaded, ran, or is mid-tween.
2. **Conversely, commerce state must never be a dependency of an animation's cleanup or scoping.** `gsap.context()` scopes and their `revert()` calls key off component mount/unmount and DOM refs, never off `cart`/`wishlist` values — an animation must not re-run or re-scope because a cart line was added (a card's "Quick add" press-feedback tween is scoped to the *button ref*, triggered by the click event directly, not by a `useEffect` watching `cart.lines.length`).
3. **The accessibility announcement channel (`commerce-provider.tsx`'s `aria-live` region driven by `announcement` state) is independent of any visual motion** and must stay that way — a screen reader user gets "Callebaut 811 Dark Chocolate Callets, 1 kg, added to demo cart" the instant `addLine()` runs, regardless of whether a card animation is playing, disabled by reduced-motion, or failed to load.
4. **`ready` (the flag `CommerceProvider` uses to avoid a hydration-mismatch flash before `localStorage` restores) has nothing to do with motion readiness** and the two must not be conflated by a future implementer reaching for "is everything ready" as a single signal — `MotionEnhancer`'s mount-time check and `CommerceProvider`'s `ready` flag solve two unrelated SSR/hydration problems (visual reveal timing vs. avoiding a cart-count flash) and should stay two separate, uncoordinated mechanisms.

**Error/fallback handling — GSAP/ScrollTrigger fails to load, or a ref is null at animation time.**
- **Script/module load failure:** if the dynamic `import("gsap/ScrollTrigger")` (or, in principle, the static `gsap` import) throws or rejects, the surrounding `useLayoutEffect` must catch it and simply not animate — not throw an unhandled rejection, not render an error boundary, not block the rest of the page. Wrap the dynamic import in try/catch (or `.catch()`) and treat failure identically to the existing `prefers-reduced-motion` early-return: DOM stays in its final static state (§ progressive enhancement above already guarantees this state is fully usable).
- **Null ref at animation time:** every new hook must guard exactly like `motion-enhancer.tsx` implicitly does via `gsap.context(fn, scope)` — if `scope.current` is null when the effect runs (possible with conditional rendering, `Suspense` boundaries resolving late, or a ref attached to an element that unmounts before the effect fires — all plausible under React 19's stricter Strict Mode double-invoke-in-dev behavior), the animation call must no-op rather than throw. Concretely: check `if (!scope.current) return;` before calling `gsap.context()`/creating triggers, and prefer selector-scoped `gsap.context(fn, scope)` calls (as the existing code already does) over directly passing a possibly-null ref into a raw `gsap.to(ref.current, ...)`, since the latter throws immediately on a null target where the former's internal selector resolution simply finds nothing to animate.
- **A ScrollTrigger target element that never renders** (e.g., conditional content, a card variant that doesn't include the animated element) must not throw either — `ScrollTrigger.create({ trigger: selector, ... })` against a selector matching zero elements is a silent no-op in GSAP, which is the desired behavior; implementers must not "fix" this by adding an assertion that throws when the trigger element is absent, since that would turn an intentionally-optional visual enhancement into a hard runtime dependency, violating the progressive-enhancement contract above.
- **React 19 / Next 16 note relevant to all of the above:** React 19's Strict Mode continues (as in React 18) to mount → unmount → remount client components once in development, which double-fires `useLayoutEffect` and exercises the `context.revert()` cleanup path twice per real mount during dev. Any new hook must be written so a rapid mount/unmount/remount cycle is safe (no double-registration of the same ScrollTrigger instance, no leaked GSAP tween references) — the existing `context.revert()` pattern already handles this correctly for the current reveal animation; new hooks must replicate the same discipline (create everything inside the effect, tear down everything via the returned cleanup, nothing created outside that effect's lifecycle).
