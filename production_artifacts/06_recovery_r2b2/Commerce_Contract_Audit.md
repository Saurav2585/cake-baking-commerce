## Per-Route Data/UI Contract

This section specifies, per route, what data is available, its shape, what the UI is allowed to claim in copy, and what commerce actions must stay functionally identical regardless of any visual/motion rework. Verified against the actual route files listed, not assumed from specs.

### Homepage — real-product rail (`src/data/real-products.ts` + wherever it's rendered, e.g. `real-product-card.tsx`)

- **Data available:** a curated **12-of-48** subset of the canonical catalog (`HOMEPAGE_SELECTION` map, confirmed 12 entries), each projected to a flat `RealProduct`: `id, sku, variantId, brand, title, department, packLabel, priceInr (rupees, not paise), image{src,alt,width,height}, badges[], note?`. `priceInr = variant.price_inr_minor / 100` — **already converted to rupees**, so any homepage code must NOT divide by 100 again; `real-product-card.tsx` re-multiplies by 100 (`pricePaise = product.priceInr * 100`) to hand back into `formatINR`, which is safe today only because every `price_inr_minor` is confirmed divisible by 100 (verified above) — this round-trip is a latent fragility, not a bug, if that invariant is ever broken.
- **Selection is data, not code:** `toRealProduct()` throws (`Unmapped homepage product`) if a catalog product ID is in `HOMEPAGE_SELECTION` but its `department_id` isn't in `DEPARTMENT_BY_ID` — a build-time guard, not a runtime one a visual redesign should ever trip.
- **Badges:** `bestseller | new | essential | tool`, purely curatorial/editorial (not derived from real sales data — there is none), rendered via `BADGE_PRIORITY` picking the single highest-priority badge to show.
- **UI must not claim:** real bestseller/sales-rank status (badges are hand-assigned merchandising labels, say so if asked, never "our top seller by sales").
- **Known live inconsistency (see item 11):** the availability line is a hardcoded `"Available in demo"` string in `real-product-card.tsx`, not derived from `variant.availability`. A motion/visual redesign of this card **may keep or restyle this string** but should not silently start deriving it from `product.availability` without also adding the field to `RealProduct` — currently `RealProduct` has no availability field at all.
- **Commerce actions that must stay identical:** `toggleWishlist(product.id, product.title)` and `addLine({...sources:[{kind:"manual"}]})` using the *canonical* `sku`/`variantId`/`productId` — confirmed these are the real canonical IDs (not a homepage-only shadow ID scheme), so a cart line added from the homepage is byte-identical in shape to one added from the PDP.

### Shop/PLP (`/shop`, `/shop/[department]`)

- **Data:** full 48-product `catalog` array (or the 7-department slice via `lockedDepartment`), each a `CatalogProduct` (canonical fields + `brandName`, `variants[]`, `media`, `content`).
- **Filter/sort UI contract (`shop-explorer.tsx`):** free-text search box (placeholder "Product, brand or SKU") matching against title+brand+SKU+applications (applications currently always empty — see item 6/7); a department `<select>` (hidden when `lockedDepartment` is set, i.e. on `/shop/[department]` the department is fixed by the route, not user-selectable); a sort `<select>` with `featured` (=Title A–Z), `price-asc`, `price-desc` (sorts by `variants[0].price_inr_minor`, i.e. first/default variant only, not min-across-variants — a multi-variant product's sort position ignores its cheaper/pricier packs).
- **Hero copy contract:** `/shop`'s hero literally states "48 parent products · 51 exact SKUs" (`src/app/shop/page.tsx`) — **any redesign must keep this number correct or remove it**; it is a live, data-adjacent claim, not decorative copy, and was previously wrong (R2B1 migration doc records it as a corrected stale "24 parent products · 38 exact SKUs" line).
- **Available in data but not exposed as a filter today:** `category_id`, `subcategory_id`, `brand_id` (as a facet chip), `product_family`, `availability`, pack-size (`normalized_sell_quantity`) — see item 7 for the full list; a UI/frontend agent adding these has real data to build against without any backend change.
- **Commerce actions:** none directly on this route besides navigation into PDP via `ProductGrid`/`ProductCard` links and wishlist-toggle from the card (`toggleWishlist`).

### Department/category (`/shop/[department]/[category]`)

- **Reachable but not linked-to:** the route exists and works — `src/app/shop/[department]/[category]/page.tsx` filters `catalog` by `department_id`+`category_id` (derived from the URL slug via `dept_${department.replaceAll("-","_")}` / `cat_${category.replaceAll("-","_")}`) and 404s (`notFound()`) if the result set is empty. **No file in the app renders a `<Link>` or `<a>` into this route** — it has no `generateStaticParams` either (unlike the department page), so it's dynamically rendered on direct hit only. Functionally correct, invisible in the current IA.
- **Subcategory tier exists in the data model:** `category_id` (14 distinct values) and `subcategory_id` (29 distinct values, e.g. `subcat_dark_couverture`, `subcat_cocoa_powder`) are present on every `CanonicalProduct` — a 3-tier taxonomy (department → category → subcategory) is fully populated in `Product_Master_Data.json`, but only the department and category tiers have any route at all, and only department has any UI entry point. A UI/frontend/IA agent wanting a full breadcrumb-driven category browse can build it directly from existing fields — no data work needed, only routing/UI work (and ideally reusing/relinking the already-working `[category]` route rather than rebuilding it).

### Search results (`/search`)

- **Data:** identical `catalog` array, identical `ShopExplorer` filter/search/sort component as `/shop` — `src/app/search/page.tsx` is a 26-line wrapper passing `initialQuery={q}` from the `?q=` param. There is no separate search index, ranking algorithm, or fuzzy-match layer; matching is a plain lowercase substring `.includes()` over the same fixed haystack described in item 6.
- **Copy contract:** hero states "Search factual canonical fields. Unsupported suitability claims are never used as filters." — this line makes an explicit promise that must be honored by any future filter additions (e.g., don't add a "best for wedding cakes" filter without a factual, sourced basis).
- **Empty state:** "No exact pantry match" / "Clear the current filters or browse all departments." — shared with `/shop` (same `ShopExplorer` component), so any visual redesign of the empty state affects both routes identically by construction.

### PDP (`/products/[slug]`)

- **Data:** one `CatalogProduct` resolved via `catalogBySlug.get(slug)` (a `Map`, O(1)); 404s via `notFound()` if the slug doesn't exist. Up to 4 "related" products from the same department (`related`), excluding itself.
- **Variant selection:** defaults to the first `available` variant (`product.variants.find(v => v.availability === "available")?.id ?? product.variants[0].id`) — falls back to the first variant at all if literally none are available (never crashes on an all-unavailable product, though none exist today). Selecting a variant updates price, pack label, availability string, and resolved media (`resolveMedia(product.id, variant.id)`, which — per item 5 — returns the **same** image for every variant of a given product unless a genuinely distinct photo was sourced, which none currently are).
- **Critical facts block:** `ingredients`, `allergens`, `storage` render via `factText()` (item 10) — currently always "Information not provided" for all 48 products; **UI must never hardcode a substitute value here even for visual polish** — an empty/placeholder-styled state for this block should be treated as the expected default, not a bug to visually "fix" by inventing text.
- **Commerce actions that must stay identical:** `addLine()` with `sources:[{kind:"manual"}]`, `toggleWishlist()`, both gated by `selectable = !["unavailable","discontinued"].includes(variant.availability)` — the button reads "Add selected pack to demo cart" when selectable, "This demo pack is unavailable" when not, and is `disabled` accordingly. The permanent disclosure "No real stock, payment, delivery or order is represented." must remain present verbatim or in equivalent substance on any redesign — it's the load-bearing anti-fraud/anti-confusion disclosure for the entire PDP.

### Wishlist (`/wishlist`)

- **Data:** `wishlist: string[]` of product IDs, held in React state + localStorage (`pantryform:wishlist:v1`), joined to the live catalog at render via `catalog.filter(p => wishlist.includes(p.id))` (item 8) — a stale/removed product id silently vanishes from the rendered grid, never crashes, but is also never pruned from storage.
- **Copy contract:** "Saved product families persist only in this browser. Choose an exact variant before adding to cart." — correctly signals that wishlist saves are at the *product* (parent) level, not the *variant/SKU* level; a redesign must not blur this distinction (e.g., must not silently add a specific pack size to cart from the wishlist without the user choosing one, since the wishlist itself carries no variant selection).
- **Loading state:** gated on `ready` (post-hydration flag from `CommerceProvider`) with a "Measuring the pantry…" busy state — must be preserved so SSR/CSR mismatch doesn't flash an empty wishlist before localStorage is read.

### Cart (`/cart`)

- **Data:** `CartState { schemaVersion: 1, revision: number, lines: CartLine[] }`, each `CartLine` denormalized with `sku, quantity, observedUnitPricePaise, productId, variantId, productTitle, variantLabel, brandName, sources[]`. Price shown is the **captured-at-add-time** `observedUnitPricePaise`, not a live re-read of the catalog's current price — a redesign must not "helpfully" re-fetch current pricing per line, since the domain model deliberately snapshots price at add-time (there is no re-pricing logic anywhere in `cart.ts` or `cart-view.tsx`).
- **Rendering safety:** every line is re-resolved against the live `catalog`/`variantsBySku` at render (item 8); a line whose product/variant no longer exists renders nothing (`return null`) — must be preserved, not replaced with a rendered "error" row that could look like a real system fault to a demo viewer.
- **Commerce actions that must stay identical:** `setQuantity(sku, quantity)` (clamped 1–99), `removeLine(sku)`, `clearCart()`, and the subtotal via `cartSubtotalPaise()` — pure line-item sum, no tax/shipping calculation exists ("Items subtotal only. Shipping and tax are not calculated." is a factual statement of current scope, not marketing copy — don't imply a shipping calculator exists visually, e.g. no "calculate shipping" affordance).
- **Recipe provenance badge:** any line with `sources.some(s => s.kind === "recipe")` shows "Added from recipe review" — must be preserved as a distinct visual signal from manually-added lines.

### Recipe-to-cart (`/recipes/[slug]/add-to-cart`)

- **Data:** one `Recipe` (from 6 total) with `ingredients[]`, each carrying `mapping_status: "mapped"|"unmapped"` and (if mapped) resolved via `recipeMappings` to a real `product_id`. 18 of 45 total ingredient lines across all 6 recipes are mapped; 27 are not (item 9) — this ratio is intrinsic to the current real catalog's coverage, not a bug to "fix" by relaxing the mapping criteria in the UI layer.
- **Solver:** `selectSmallestSufficient()` / `selectSingleVariant()` (`recipe-solver.ts`) compute the minimum-waste pack combination for a required quantity, filtered to variants matching the ingredient's unit `kind`+`canonical_unit` and excluding `unavailable`/`discontinued` variants. Purely deterministic, no randomness — a given `(required, options)` pair always returns the same `PackSelection` (tie-broken by sorted `variantId` join, then price), so visual/motion changes must not introduce any nondeterminism into which pack combination is proposed.
- **Auto-include rules that must stay identical:** an ingredient starts pre-checked only if `!optional && pantry_default === "assume_needed"`; unmapped ingredients (`!product`) render "No bounded catalog mapping..." with a **disabled** checkbox and are explicitly skipped in `addSelected()` even if somehow checked — a redesign must preserve both the visual disable state and the logical skip, not just one or the other (item 9).
- **Cart lines added from here** carry `sources: [{kind:"recipe", recipeId, recipeRevision:"phase5b", mappingId: ingredient.id}]` — the `recipeRevision` literal `"phase5b"` is hardcoded (not derived from `catalogRevision` or the recipe's own schema version) and should be revisited if recipe data ever gets a real revision scheme, but is not a defect for this audit's scope (informational only).
