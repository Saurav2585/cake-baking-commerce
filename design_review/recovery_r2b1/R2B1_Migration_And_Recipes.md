# Recovery R2B1 — Canonical Migration Notes & Recipe Remapping Report

## Canonical migration notes

The existing canonical data model (`production_artifacts/05_catalog_production/Product_Master_Data.json`, `SKU_Variant_Data.json`, `Product_Content_Records.json`, `Catalog_Asset_Manifest.json`, `Recipe_Product_Mapping.json`) was **adapted in place**, not forked. `src/lib/domain/catalog.ts` — the module every route (`/`, `/shop`, `/products/[slug]`, `/search`, `/recipes/*`, `/cart`, `/checkout`) reads from — required only two changes:

- `BRAND_NAMES` now maps the 30 real brand IDs to real brand names (the 8 fictional brand entries — Fieldnote, Measureloom, Nibform, Tintfold, Fillmark, Detailbench, Formstead, Packplane — are removed entirely, not just unused).
- The "Unknown fictional brand" error message was reworded, since brands are no longer fictional.

`resolveMedia()`, `chooseAsset()`, `publicAssetPath()` and every component that reads `catalog`/`variantsBySku`/`variantsById` are **unchanged** — the 48 real products flow through exactly the same join/media-resolution path the 24 fictional products used, because the new asset-manifest records were built in the same shape (`role`, `relationships.{product_ids,variant_ids,skus,recipe_ids}`, `derivatives[{purpose,path,width,height,checksum}]`, `alt_text.text`) the resolver already expects.

**What replaced what:**
- `Product_Master_Data.json` / `SKU_Variant_Data.json` / `Product_Content_Records.json`: the 24 fictional products/38 variants/24 content records are fully replaced by 48 real products/51 variants/48 content records. Generated by `tools/generate_real_catalog_data.mjs` from the hand-authored source table `tools/real_catalog_source.mjs` (every field traces to the R1 provenance register).
- `Catalog_Asset_Manifest.json`: the 62 fictional `product_packshot` records (24 primary + 38 variant-owned, deterministic-SVG-generated) are replaced by 48 real-photography `product_packshot` records, one per product (no variant-owned images — see below). The 13 kept `recipe`/`department` editorial records are **untouched**. Generated by `tools/generate_real_catalog_assets.mjs`.
- `data/Catalog_Data_Index.json`: expected counts and department distribution updated to 48/51/48/7×7+6.

**Why no variant-owned images:** the fictional pipeline generated a distinct label composite per SKU. Real photography doesn't have that — a manufacturer very rarely shoots a different photo per pack size of the same product line, and R2B1 only ever sourced one real photo per product. Per R2B1 Section 4 ("variant-owned image only where packaging genuinely differs"), every variant of a multi-variant product (Callebaut 811, Nutella, Urban Platter Vanilla Extract) intentionally resolves to the **same** product-level image — confirmed by a dedicated unit test (`catalog.test.ts`, "resolves media for a product that shares one packshot across pack-size variants").

**Missing-image handling:** any product without a locally sourced real photo at build time renders an honest, non-branded "Image not yet available" placeholder graphic (`public/assets/catalog/real/_placeholder_*.webp`) rather than a fabricated or AI-recreated packshot. This required **no changes** to `resolveMedia()` — every product's manifest record always resolves to *some* local file (real or placeholder), so the module-level `catalog.map()` join in `catalog.ts` never throws. See the provenance/validation report for the current sourced/missing count.

**Validator rewrite:** `tools/validate_catalog_assets.js` was rewritten. The old version hardcoded `product_count !== 24` and required every product asset to be an SVG with baked-in "PORTFOLIO DEMO"/"PANTRYFORM" label text produced by a specific deterministic-composite method — assumptions specific to the fictional illustration pipeline that do not apply to real photography. The new version checks what R2B1 Section 8 requires instead: resolvable relationships, exactly one primary packshot per product, local (never remote/hotlinked) files with matching SHA-256 checksums and dimensions, non-empty alt text, and a `provenance` block (confidence status, source URL, source type) on every record. It still validates the kept recipe/department editorial records' file integrity. `tools/validate_catalog_data.js` needed no rewrite — it already read its expected counts from `data/Catalog_Data_Index.json` rather than hardcoding them.

**Homepage wiring (`src/data/real-products.ts`):** previously a standalone 12-entry array duplicating brand/price/pack/image data. It now derives every field from `catalog` (12 canonical products selected by ID, per R2B1 Section 7), keeping only homepage-curatorial data (which merchandising badge each one wears) that has no canonical home. `RealProductCard`'s "Quick add" now adds the **real** canonical SKU/variant ID instead of a synthetic `{id}_default` — so a line added from the homepage is the same cart line a future PLP/PDP add-to-cart would produce. This let `cart-view.tsx` drop its homepage-specific rendering branch entirely (the generic canonical-catalog path now covers homepage-added lines too), and let `layout.tsx` drop the separate `REAL_PRODUCT_SKUS` allowlist addition (homepage SKUs are already canonical SKUs).

**Stale-fictional-catalog leakage prevention:** enforced in two places — `validate_catalog_assets.js` fails the build if any product's `brand_id` matches the 8 retired fictional brand IDs, or if any product ID doesn't start with `prod_real_`; `catalog.test.ts` asserts the same at the unit level plus that none of the 8 fictional brand names resolve through `BRAND_NAMES`.

**Product-truth copy fixes:** two PDP strings ("... · fictional product label", "... · fictional demo state") and one About-page paragraph ("Every product, brand, price and availability state is fictional") were factually wrong once products became real — only price/availability are fictional demo fixtures, not the products or brands. Corrected to "· demo listing" / "· demo fixture" and to an accurate sentence distinguishing real product/brand identity from fictional pricing. The stale "24 parent products · 38 exact SKUs" line on `/shop` is now "48 parent products · 51 exact SKUs".

## Recipe remapping report

10 fictional products were referenced across the 6 recipes' 27 original mappings. Each was re-evaluated against the real 48-product catalog and mapped **only** where the ingredient/pack relationship is genuinely truthful — nothing was force-mapped.

| Fictional ingredient concept | Real replacement | Verdict |
|---|---|---|
| Plain flour | Pillsbury Maida | Mapped — maida *is* all-purpose wheat flour |
| Baking cocoa powder | Weikfield Cocoa Powder | Mapped — genuine unsweetened cocoa powder |
| Baking powder | Weikfield Double Action Baking Powder | Mapped — same product category |
| Vanilla essence | Urban Platter Premium Vanilla Extract | Mapped — extract and essence are functionally interchangeable in baking use |
| Dark chocolate chips | Morde Dark Compound Chocolate Chips | Mapped — genuine chocolate chip product |
| White rolled fondant | Bakersville Vizyon Sugar Paste (White) | Mapped — genuine white rolled fondant |
| Caster sugar | *(none)* | **Unmapped** — the real catalog's only sugar is Eagle Icing Sugar, a different (finer, powdered) granulation not suited to creaming into batter; substituting it would misrepresent the recipe |
| Strawberry filling | *(none)* | **Unmapped** — no strawberry or fruit-filling product exists in the real catalog |
| Orange emulsion | *(none)* | **Unmapped** — no orange-flavour product exists in the real catalog |
| Neutral glaze | *(none)* | **Unmapped** — no glaze product exists in the real catalog |

Result: **18 explicit mappings** (down from 27), **27 unmapped lines** (up from 18 — the pre-existing 18 structural unmapped lines for eggs/milk/oil/butter/buttercream, which no bounded catalog ever covered, plus 9 newly and honestly unmapped lines above). Total recipe ingredient lines is unchanged at 45. `Recipe_Master_Data.json`'s per-line `mapping_status` field was updated to agree with `Recipe_Product_Mapping.json` for all 9 changed lines (enforced by `validate_catalog_data.js`).

`RecipeReview` (`src/components/recipe-review.tsx`) already renders unmapped ingredients as a visible, un-checkable "No bounded catalog mapping. Keep as a visible pantry check; it will not be added." row — this required no UI code change, only correct data.
